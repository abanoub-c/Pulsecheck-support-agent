Finished with timing data: **Thought for 2 seconds** (computed from step timestamps; **Thought for under a second** when shorter), followed by muted metadata such as **4 steps, 2 tools**. - Toggle contents are a muted IBM Plex Mono, `--surface`, bordered, internally scrollable audit container grouping Steps, Tool calls and State. Steps are an ordered vertical timeline with numbered label, node name in small caps and one or two description lines; kinds include classification (categories/confidence/router’s short reasoning), clarification, dispatch, tool call, tool result (ok/error chip), reply, escalation. New steps animate in and latest is highlighted. Tool calls show tool name in mono, collapsible pretty JSON args, collapsible truncated result, duration if available and ok/error chip. State lists category, pending categories, confidence, clarify attempts, turn count, resolution status and escalation reason. This is an audit trail, not raw reasoning; never show raw model chain-of-thought.
- If an escalation ends without an assistant message, place the toggle above the escalation notice. Replay toggles for each turn from `GET /api/threads/{thread_id}` after reload. Toggles clear when a new thread starts.
- Composer has text input and Send button; disable while reply streams. Enter sends; Shift+Enter adds a line. Show character count near the 500-character limit.
- Empty state shows the selected customer’s suggested prompt chips. Streaming shows typing indicator and toggle filling in step by step. Escalated state shows a plain-language banner explaining it was passed to a human specialist and why. Error state shows inline message with Retry.
- After 3 seconds without response, show **Waking up the agent** with elapsed timer; poll `/api/health` every 2 seconds for up to 90 seconds before failing. After escalation, poll `GET /api/threads/{thread_id}` every 5 seconds so the human reply appears after Ops acts.

- Below KPIs, use two columns (`1.35fr` and `1fr`) stacking under 900px. Escalation queue table is horizontally scrollable on small screens, with Customer (company and ID), Reason (status chip), Proposed action, Waiting time. Clicking a row selects it; first row is selected by default. Filter by reason and Pending/Resolved status.
- Selected escalation detail panel shows company, ID, plan, account status; **Why it was escalated** in plain words; **Agent’s proposed action** in mono block (e.g. refund call and amount); **Conversation** summary with link or drawer to full transcript; editable **Message to customer** textarea prefilled with suggested reply; buttons **Approve**, **Edit**, **Reject**.
- Approve sends the message as-is. Edit focuses the textarea and changes the button to **Send edited**. Reject asks for a short note first. After a decision, optimistically update, show toast and move the row to Resolved. Poll the queue every 10 seconds. Empty state says **All caught up**.
- Reason chips: `refund_exceeds_threshold` warning; `loop_guard_exceeded` danger; `tool_call_failed` danger; `customer_requested_human` info; `low_confidence`, `clarification_exhausted`, and `uncategorized_request` neutral.
- Business behavior represented in copy and states: refunds under $100 auto-approve only after the customer confirms the exact amount; refunds of $100 or more are held for manager review. Cancellation needs explicit customer yes; offer a retention discount first if the customer has not used one. Retention discount is 5–25% for 1–6 months; up to 20% and 3 months is auto-approved; more goes to review; one per account. Plan downgrades credit unused value to account balance applied to next invoice, with no charge today. Upgrades charge the prorated difference immediately. Goodwill credits (e.g. downtime) are handled by billing agent, not refund agent. Agent never claims an action it did not take.

## [x] Outcome 6 — BFF contracts, synthetic services, security, and failure handling

- Architecture is Browser → Node.js server (BFF) → agent service (Python) → CRM API (Python). Browser talks only to Node; API keys and internal URLs never reach browser bundle. The Python side may sleep after 15 minutes idle; first request can take 30–60 seconds; handle cold start gracefully.
- CRM API is read-only to this app; mutations happen only through agent service. CRM paths: `GET /health`; `GET /customers/{customer_id}`; `GET /subscriptions/{customer_id}`; `GET /invoices/{customer_id}`; `GET /incidents?status=open|resolved`; `GET /monitors/{customer_id}/stats?days=30`; `GET /tickets?customer_id=&category=&days=&limit=` (`customer_id` required, `days` 1–30); `GET /escalations?status=pending&customer_id=`; dev-only `POST /admin/reseed`, disabled when `PULSECHECK_ENABLE_ADMIN=0`. Customer response fields: customer_id, company_name, contact_name, contact_email, signup_date, tier, account_status. Invoice includes invoice_id, amount, currency, status, invoice_date, failure_reason. Ticket includes ticket_id, category, subject, status, created_at. Escalation includes escalation_id, customer_id, ticket_id, category, confidence, reasoning, proposed_action, conversation_summary, status, decision, decision_note, created_at, resolved_at.
- Browser-facing BFF routes add validation/rate limits and forward to `AGENT_API_URL`: `GET /api/health` returns status/readiness; `POST /api/chat` takes thread_id/customer_id/message and streams Server-Sent Events (use fetch plus ReadableStream since EventSource is GET-only); `GET /api/threads/{thread_id}` returns customer_id, status (open/resolved/escalated), messages (role/content/at), state, steps; `GET /api/escalations?status=pending` returns CRM escalation fields plus thread_id and customer company name; `POST /api/escalations/{escalation_id}/decision` takes action approve/edit/reject, customer_message, note and resumes paused thread; `POST /api/demo/reset` reseeds CRM and returns status.
- SSE events: `step` {id, at, node, kind, title, detail}; `message` {role: assistant, content}; `state` {category, pending_categories, confidence, clarify_attempts, turn_count, resolution_status, escalation_reason}; `escalated` {escalation_id, reason}; `error` {message, retryable}; `done`. Nodes: context_manager, router, dispatch, billing, technical, refund, billing_tools, technical_tools, refund_tools, escalate. Step kinds/details: classification (categories list, confidence, reasoning, wants_human, is_smalltalk); clarification (question); dispatch (category); tool_call (tool,args); tool_result (tool,ok,result); reply (preview); escalation (reason,escalation_id).

Ticket statuses resolved, closed or solved are Solved; all others Unsolved.
